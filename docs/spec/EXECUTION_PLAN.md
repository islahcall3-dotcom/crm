0.2 بوابة المرحلة (Phase Gate)

لا انتقال إلا إذا تحقق كل ما يلي:

كل معايير المرحلة PASS بدليل (لا PARTIAL ولا FAIL).

tag باسم phase-N منشأ.

معيار PARTIAL/FAIL يُصلَح قبل الانتقال. إن تعذّر إصلاحه لسبب خارج سيطرتك فتوقف عند نقطة التوقف المناسبة (§0.3).

0.3 نقاط التوقف الإلزامية (Hard Stops) — الوحيدة التي توقف التنفيذ
#	متى تتوقف
H-01	غموض في قاعدة عمل يغيّر البيانات أو السلوك ولا توجد له توصية آمنة (R-06). اطرح السؤال بخيارات وتوصية.
H-02	أي أمر على Google Cloud حقيقي أو دومين: يحتاج GO STAGING ثم GO PRODUCTION (Phase 8).
H-03	إجراء مدمّر أو غير قابل للتراجع (حذف بيانات فعلية، force push، تعديل خارج المشروع).
H-04	مطلوب مني شيء لا تستطيع الحصول عليه بنفسك: ملف بيانات، حساب، سر، قرار Region.
H-05	تعثر حقيقي: محاولتان فاشلتان لنفس المشكلة، أو فشل بوابة مرحلة لا يمكن إصلاحه.
H-06	اكتشاف أن قراراً مقفلاً (§2) أو معيار قبول لا يمكن تحقيقه كما هو. اطلب اعتماد انحراف ولا تتجاوزه بصمت.

ما عدا ذلك لا تتوقف ولا تطلب اعتماداً. الأسئلة غير الحرجة تُحسم بتوصيتك وتُسجَّل كافتراض A-xx في DECISIONS.md وتظهر في تقرير المرحلة، وسأراجعها لاحقاً.

عند التوقف اكتب: رقم النقطة (H-xx)، السبب، ما جرّبته، الخيارات مع توصيتك، وما الذي سيُستأنف عند ردّي.

1. بروتوكول الدقة والأمانة (غير قابل للتفاوض)
#	القاعدة
R-01	لا "تم" بدون دليل. كل ادعاء إنجاز مرتبط بدليل قابل لإعادة التشغيل: أمر حرفي + ناتجه، أو ملف، أو لقطة شاشة من تطبيق يعمل فعلاً.
R-02	شغّل قبل أن تُبلغ. لا تقرير قبل تشغيل npm run verify وتشغيل التطبيق فعلياً وتجربة المسارات الأساسية.
R-03	لا تُضعف الاختبارات. ممنوع حذف أو تعطيل أو تخفيف اختبار فاشل لتمرير البوابة. أصلح الكود. إذا كان الاختبار نفسه خاطئاً فاشرح السبب صراحةً في التقرير.
R-04	لا Mock لقاعدة البيانات ولا بيانات وهمية. الاختبارات تعمل على PostgreSQL حقيقي. الـ Fixtures تعيش داخل الاختبارات فقط.
R-05	تحقق من المكتبات قبل الاستخدام. اقرأ وثائق أو Types النسخة المثبتة فعلياً، ولا تعتمد على الذاكرة. تأكد أن الحزمة موجودة في الـ registry قبل إضافتها. ثبّت الإصدارات (lockfile). لا تضف مكتبة ثقيلة لمهمة بسيطة.
R-06	لا تخمّن قواعد العمل. غموض يغيّر البيانات أو السلوك ← توقف واسأل بخيارات وتوصية. غموض شكلي صغير ← افتراض مسجّل A-xx في docs/DECISIONS.md.
R-07	التزم بالنطاق. لا تضف ميزات غير مطلوبة ولا وحدات المستقبل (§54)، لكن لا تُغلق الباب أمامها.
R-08	القرارات المقفلة (§2) لا تتغير بصمت. أي تغيير = انحراف D-xx يُطلب اعتماده.
R-09	مراجعة ذاتية قبل التقرير. أعد قراءة كل معيار قبول وقارنه بالكود الفعلي (وليس بذاكرتك)، واذكر أي فجوة.
R-10	الأمانة في التقرير. PARTIAL وNOT DONE مقبولان ومطلوبان عند الحقيقة. تقرير كله PASS تُكتشف فيه فجوات لاحقاً = فشل المرحلة.
R-11	الأمان. لا أسرار في الريبو أو اللوجات أو الـ Frontend. لا Credentials حقيقية في التطوير. لا أوامر ضد Google Cloud حقيقي بدون GO. لا أوامر مدمرة (drop / rm -rf / force push) بدون تأكيد.
R-12	العزل. اعمل داخل مجلد المشروع فقط، ولا تعدّل ملفات خارجه.
R-13	كود نظيف. TypeScript strict، لا any بلا تبرير، لا كود ميت، لا TODO أو placeholder في كود مُسلَّم، تعليقات للـ "لماذا" فقط.
R-14	Git. Commits صغيرة ومترابطة بالإنجليزية (Conventional Commits). ضع tag في نهاية كل مرحلة: phase-N (وphase-N-v2 بعد التعديلات).
R-15	رسائل المستخدم النهائي بالعربية المبسطة الواضحة. لا Stack Traces ولا رسائل تقنية تظهر له.
R-16	التعثر. إذا فشلت محاولتان لحل نفس المشكلة: توقف، اشرح ما جرّبته، وقدّم خيارات. لا تدور في حلقة.
R-17	لا بيانات شخصية في اللوجات (هواتف، عناوين، كلمات سر، Tokens).
R-18	تخطيط قبل الكود. Mini-Plan لكل مرحلة (§0.6). لا كود قبل تحديد الشرائح والاختبارات المقابلة لمعايير القبول.
R-19	شرائح صغيرة خضراء. لا تترك المستودع في حالة فاشلة بين شريحتين. شغّل الاختبارات المتعلقة بعد كل شريحة، وverify كاملاً في نهاية المرحلة.
R-20	مراجعة عدائية (Adversarial Review) قبل كل بوابة. بقبعة مراجع مستقل حاول كسر عملك: مدخلات شاذة، صلاحيات ناقصة، سباق بين جلستين، حدود التواريخ، أرقام وحروف عربية، شاشة الموبايل. دوّن ما وجدته وأصلحته في التقرير.
R-21	الحالة في الملفات لا في الذاكرة. PROGRESS.md وDECISIONS.md والتقارير هي الحقيقة. بعد أي جلسة طويلة أو انقطاع أعد بناء السياق منها.
R-22	لا تجمّل الحالة لتواصل الانتقال. في الوضع المتواصل يزداد إغراء تمرير البوابة. تمرير معيار بلا دليل = فشل للمرحلة كلها.
2. القرارات المقفلة (Locked Decisions)

هذه قرارات متخذة. لا تعدّلها إلا عبر انحراف D-xx معتمد.

#	القرار
L-01	Architecture: Modular Monolith. خدمة Node.js واحدة تقدّم REST API على /api/v1/* وتخدم ملفات الواجهة المبنية. Same-origin (لا CORS مفتوح، ولا مشاكل Cookies).
L-02	Backend: Node.js (LTS الحالي) + TypeScript strict + Fastify + Zod للـ Validation. طبقات: routes → controllers → services → repositories.
L-03	Frontend: React + TypeScript + Vite + Tailwind (بخصائص Logical مثل ms-/me-/ps-/pe- لدعم RTL) + مكوّنات مبنية على Radix Primitives (Accessibility) + TanStack Query + React Router + React Hook Form + Zod.
L-04	Database: PostgreSQL. timestamptz (UTC) للأوقات، وdate للتواريخ الصرفة. مفاتيح uuid (v7) + customer_code تسلسلي مقروء للبشر.
L-05	Auth: Server-side Sessions في DB. Token عشوائي 256-bit يُخزَّن Hash (SHA-256) فقط. Cookie بـ __Host- prefix + HttpOnly + Secure + SameSite=Lax. Idle 8 ساعات، Absolute 7 أيام (قابلة للضبط). Argon2id للـ Passwords، حد أدنى 10 أحرف.
L-06	CSRF: Token (Double-Submit) في Header + فحص Origin على كل POST/PUT/PATCH/DELETE.
L-07	RBAC: Deny-by-default. الـ Permissions معرّفة كثوابت في الكود وتُزامَن مع DB عند التشغيل (idempotent). الأدوار قابلة للتعديل من الواجهة. كل Route يعلن صراحةً permission أو public.
L-08	Realtime: SSE + Postgres LISTEN/NOTIFY (للعمل عبر أكثر من Instance). الأحداث تلميحات إبطال (entity, id, version, action) بدون بيانات شخصية، والعميل يعيد الجلب بصلاحياته. Fallback: Polling عند انقطاع SSE.
L-09	Concurrency: عمود version على كل كيان قابل للتعديل. التعديل يتطلب version ويُرفض بـ 409 عند عدم التطابق مع إرجاع الحالة الحالية.
L-10	الحذف: Soft Delete للعملاء والزيارات والموظفين والتواصل. جدول audit_logs Append-only (Trigger يمنع UPDATE/DELETE). بيانات الإعدادات المرجعية تُعطَّل ولا تُحذف إذا كانت مستخدمة.
L-11	الوقت: التوقيت التجاري Africa/Cairo. "اليوم" يُحسب في الـ Backend بهذا التوقيت.
L-12	الواجهة: عربية RTL بالكامل، أرقام غربية (0-9)، تاريخ DD/MM/YYYY، خط عربي Self-hosted (لا CDN وقت التشغيل، كي تعمل CSP الصارمة). Light/Dark.
L-13	التصدير: Excel (xlsx) + CSV (UTF-8 مع BOM + حماية من CSV Injection) + PDF (Headless Chromium من قالب HTML بخط عربي مضمّن). صحة العربية في PDF تُثبت بدليل بصري في Phase 6.
L-14	بدون Service Worker/PWA في v1 (تجنباً للنسخ القديمة المخزّنة). ملفات مبنية بـ Hash، وindex.html بـ no-store، ونقطة /api/v1/version.
L-15	الاختبارات: Vitest + اختبارات تكامل على Postgres حقيقي + Playwright (E2E + Multi-context + Responsive).
L-16	لا Seed للعملاء أو المستخدمين في أي بيئة. يُستثنى أداة بيانات اصطناعية للأداء، تعمل فقط عند ALLOW_SYNTHETIC_DATA=true وتُرفض برمجياً في Production.
L-17	النطاق v1: كما في الـ Spec. المبيعات والفواتير والمخزون خارج النطاق، وجدول products لا يُنشأ الآن.
L-18	الحجم المستهدف: حتى 20,000 عميل و100,000 زيارة، ~10 مستخدمين متزامنين.
L-19	النشر: Cloud Run + Cloud SQL (PostgreSQL) + Secret Manager + Cloud Scheduler + Artifact Registry. المنطقة (Region) تُقرَّر في Phase 8 مع المستخدم بعد التحقق من دعم الخدمتين.
L-20	اللغات: واجهة عربية. الكود والـ Commits بالإنجليزية. الوثائق عربية مختصرة مع مصطلحات إنجليزية.
قرار مفتوح (يقترحه الـ Agent في Phase 1)

5. قالب تقرير المرحلة

يُحفظ في docs/phase-reports/PHASE-N-REPORT.md (و-v2 بعد التعديلات)، ويُعرض على المستخدم كاملاً في رد المرحلة دون انتظار رد منه:

text
# PHASE N REPORT — <اسم المرحلة>   [v1]
1. الملخص (3 أسطر كحد أقصى)
2. جدول تتبع المتطلبات:
   | المعيار | الوصف | الدليل (أمر/ملف/لقطة) | الحالة: PASS / PARTIAL / FAIL / NOT DONE |
3. ما تم بناؤه (الملفات والمجلدات الرئيسية)
3ب. المراجعة العدائية: ما حاولت كسره، ما وجدته، ما أصلحته
4. نتائج verify (جدول Suites + الأمر الحرفي + الناتج المختصر)
5. الانحرافات عن الخطة (D-xx) وسبب كل واحد
6. الافتراضات (A-xx) التي أحتاج تأكيدها
7. المشاكل والمخاطر المعروفة
8. كيف تشغّل هذه النسخة (أوامر حرفية) + سيناريو المراجعة اليدوية للمستخدم
9. الأدلة: مسارات لقطات الشاشة/اللوجات في docs/phase-reports/evidence/phase-N/
10. ما لم يُنجز — بصراحة
11. Git: commit hash + tag
12. بوابة المرحلة: PASSED / FAILED، ثم "الانتقال تلقائي إلى PHASE N+1" أو نقطة التوقف H-xx وسببها

قواعد الأدلة: لقطات الشاشة من تطبيق يعمل فعلاً على DB حقيقية. الأوامر حرفية مع ناتج حقيقي. لا "يُفترض أنه يعمل".

PHASE 8 — النشر والنسخ الاحتياطي والفحص النهائي

شرط البدء (من المستخدم): مشروع Google Cloud جاهز + الفوترة مفعّلة + قرار الـ Region + الدومين (اختياري) + من سيشغّل أوامر gcloud. الـ Agent يطلب هذه المعلومات ولا يفترضها (H-04).

ترتيب العمل في Phase 8 حتى لا يتعطل التنفيذ: أنجز أولاً كل ما لا يحتاج Google Cloud حقيقياً (Dockerfile، السكربتات، Smoke Tests، الـ Runbook، الوثائق، Final QA المحلي، البنود P8-02 و03 و04 كسكربتات و09 كتوثيق و11 و12)، ثم توقف عند H-02 واطلب المتطلبات وGO STAGING في رسالة واحدة واضحة.

قاعدة صارمة: لا يُنفَّذ أي أمر على Google Cloud حقيقي قبل رسالة GO STAGING (ثم GO PRODUCTION منفصلة). قبل كل GO اعرض قائمة الأوامر وما سيفعله كل منها.

ID	المعيار
P8-01	تأكيد المتطلبات المسبقة من المستخدم، وتوثيق الـ Region المختار بعد التحقق من دعم Cloud Run وCloud SQL فيه من الوثائق الرسمية.
